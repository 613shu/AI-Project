# 🏠 הבוט המשפחתי – מערכת RAG עם LlamaIndex

בוט שיחה משפחתי שעונה בעברית על שאלות על בני המשפחה: ימי הולדת, גילאים, קשרים משפחתיים, תחביבים, תכונות, ימי נישואים ועוד.
הבוט עונה **רק מתוך מאגר מידע ייעודי**, באמצעות ארכיטקטורת RAG (Retrieval-Augmented Generation) שמומשה בספריית **LlamaIndex**.

**🌐 האתר החי:** https://ai-project-qpyn.onrender.com/
(האתר מוגן בסיסמה משפחתית. בתוכנית החינמית של Render השרת "נרדם" אחרי זמן ללא שימוש, ולכן הטעינה הראשונה עשויה להימשך כחצי דקה עד דקה.)

## ארכיטקטורת המערכת

המערכת בנויה משני תהליכים נפרדים, כפי שנלמד בקורס:

### 1. תהליך הטעינה (Offline – Ingestion) – `ingest.py`

```
קבצי טקסט (data/)
   ↓  SimpleDirectoryReader
Documents
   ↓  SentenceSplitter (chunk_size=512, chunk_overlap=50)
Nodes (מקטעים)
   ↓  GoogleGenAIEmbedding (gemini-embedding-001)
וקטורים
   ↓  ChromaVectorStore
ChromaDB (collection בשם family, בתיקייה ./chroma_db)
```

בכל הרצה ה-collection נמחק ונבנה מחדש, כך שלא נשארים מקטעים ישנים או כפולים אחרי עריכת קבצים.

### 2. תהליך השאלה (Online – Query) – `server.py` / `app.py`

```
שאלת המשתמש (+ היסטוריית השיחה)
   ↓  1. ניסוח מחדש (condense_prompt): שאלת המשך → שאלה עצמאית
   ↓  2. Embedding של השאלה המנוסחת
   ↓  3. Retrieval וקטורי מ-ChromaDB (similarity_top_k=5)
   ↓  3א. CalendarPostprocessor: הוספת "לוח אירועים מחושב" (התאריך העברי של היום,
   ↓      ימי הולדת וימי נישואים ב-7 הימים הקרובים) כמקטע נוסף
   ↓  4. הרכבת ההקשר (context_prompt) + הוראות (system_prompt) + היסטוריה
   ↓  5. Gemini (gemini-3.5-flash) מייצר תשובה
תשובה בעברית → לממשק
מקורות (score, שם קובץ, קטע טקסט) → לטרמינל / ללוג השרת
```

השלבים 1–5 ממומשים ב-`index.as_chat_engine(chat_mode="condense_plus_context")` של LlamaIndex, עם `ChatMemoryBuffer` נפרד לכל שיחה. שלב 3א ממומש כ-`node_postprocessor` (ראו [אתגר 4](#4-שאלות-תלויות-זמן-למי-יש-יום-הולדת-השבוע)).

### 3. שכבת הקליינט

```
דפדפן (React, static/index.html)
   │  POST /api/chat   { session_id, message, history }
   │  POST /api/reset  { session_id }
   ▼
FastAPI (server.py) ── מילון chat_engines לפי session_id ── מנוע RAG
```

- **ממשק React:** עמוד יחיד ללא שלב build (React ו-Babel נטענים מ-CDN), עיצוב חם בכיוון RTL, מסך פתיחה עם שאלות לדוגמה, הצעות לשאלות המשך, ורשימת "השיחות שלי" שנשמרת ב-`localStorage` של הדפדפן.
- **ממשק Streamlit:** ממשק פשוט לפיתוח ולבדיקות מקומיות, עם אותו מנוע ואותן הוראות.
- **`prompts.py`:** ההוראות לבוט נמצאות בקובץ אחד, משותף לשני הממשקים, כדי ששינוי יתבצע במקום אחד בלבד.

## הבחירות הטכנולוגיות ונימוקיהן

| רכיב | הבחירה | הנימוק |
|---|---|---|
| שפה | Python 3.12 | דרישת התרגיל |
| Framework ל-RAG | LlamaIndex | דרישת התרגיל; רכיבים מוכנים לטעינה, חלוקה, אינדקס ו-chat engine |
| Vector DB | ChromaDB (מקומי, persistent) | מתאים לפרויקט בהיקף קטן, ללא שרת חיצוני; נלמד בקורס |
| מודל Embeddings | `gemini-embedding-001` | יציב, תומך היטב בעברית, באותו ספק כמו מודל השפה (מפתח אחד) |
| מודל שפה | `gemini-3.5-flash` | איזון טוב בין איכות, מהירות ועלות. המשימה אינה דורשת חשיבה מורכבת |
| Temperature | 1.3 | ראו אתגר 5 – העלאה מכוונת כדי למנוע תשובות יבשות ושבלוניות |
| Chunking | `SentenceSplitter`, ‏512 טוקנים, חפיפה של 50 | הקבצים קצרים ובמבנה קבוע, ורוב השאלות הן על אדם מסוים; המטרה היא שכל אדם יישמר במקטע אחד או בכמה מקטעים בודדים. חלוקה לפי משמעות (Semantic) יקרה יותר ולא נדרשת, כי הקבצים כבר מחולקים לפי כותרות |
| top_k | 5 | מאפשר לשלוף את האדם עצמו, קרובי משפחה רלוונטיים ואת הקובץ הכללי, ומשפר שאלות שחוצות את המשפחה ("מי אוהב לבשל?") |
| שיטת חיפוש | וקטורית בלבד | שם האדם נכלל ב-metadata וב-embedding, מה שמקטין בלבול בין שמות. חיפוש מילות מפתח (BM25) פחות מתאים לעברית בגלל אותיות השימוש (ו, ה, ל, ש, ב) |
| Query Expansion | ללא | עם מאגר קטן ו-top_k=5 הסיכון לפספס נמוך. הניסוח מחדש של שאלות המשך אינו הרחבה, אלא השלמת הקשר מהשיחה |
| זיכרון שיחה | `condense_plus_context` + `ChatMemoryBuffer(token_limit=3000)` | ראו אתגר 2 |
| תאריכים עבריים | `pyluach` + `family_calendar.py` | חישוב דטרמיניסטי של ימי הולדת וימי נישואים, במקום להסתמך על אחזור וקטורי ועל חישוב של המודל. ראו אתגר 4 |
| קליינט | React + FastAPI (ובנוסף Streamlit) | חוויית משתמש מלאה למשפחה; Streamlit נשאר לבדיקות מהירות |
| אחסון | Render (תוכנית חינמית) | פריסה פשוטה מ-Git, עם משתני סביבה למפתח ולסיסמה |

## הוראות התקנה והרצה

### דרישות מקדימות
- Python 3.12
- מפתח API של Google Gemini (בפרויקט שמחובר לחיוב)

### 1. התקנת החבילות
```bash
pip install -r requirements.txt
```
להרצת ממשק ה-Streamlit צריך גם:
```bash
pip install streamlit
```

### 2. הגדרת המפתח
יוצרים קובץ `.env` בתיקיית הפרויקט:
```
GEMINI_API_KEY=המפתח_שלך
```
(אופציונלי) לבדיקה שהמפתח עובד ולהצגת המודלים הזמינים:
```bash
python check_models.py
```
(אופציונלי) לבדיקת לוח האירועים, בלי מודל ובלי מפתח:
```bash
python family_calendar.py
```

### 3. בניית המאגר
```bash
python ingest.py
```
יש להריץ מחדש בכל פעם שמשנים קבצים בתיקייה `data`.

### 4. הפעלת הבוט

**ממשק React (הממשק הראשי):**
```bash
python server.py
```
ואז לפתוח בדפדפן: http://localhost:8000
(הממשק טוען React וגופנים מהאינטרנט, ולכן נדרש חיבור לרשת.)

**ממשק Streamlit (לבדיקות):**
```bash
python -m streamlit run app.py
```

### מתי שינוי נכנס לתוקף
| מה שונה | מה עושים |
|---|---|
| קבצים ב-`data` | `python ingest.py`, ואז הפעלה מחדש של הבוט (גם לוח האירועים נקרא מחדש רק בהפעלה מחדש) |
| `prompts.py` | הפעלה מחדש של `server.py` (ב-Streamlit: שיחה חדשה או רענון) |
| מודל / temperature | עצירה (Ctrl+C) והרצה מחדש |

## פריסה ל-Render

הפריסה מוגדרת בקובץ `render.yaml`:
- **Build:** ‏`pip install -r requirements.txt && python ingest.py` – המאגר נבנה מחדש מתוך `data` בכל פריסה, ולכן `chroma_db` לא נשמר ב-Git.
- **Start:** ‏`python server.py` – השרת קורא את הפורט ממשתנה הסביבה `PORT`.
- **משתני סביבה** (מוגדרים בלוח הבקרה של Render, לא בקוד):
  - `GEMINI_API_KEY` – מפתח ה-API.
  - `FAMILY_PASSWORD` – סיסמה משפחתית. כשהמשתנה מוגדר, השרת דורש סיסמה (HTTP Basic Auth) לכל בקשה. בהרצה מקומית, בלי המשתנה, אין סיסמה.

## הצגת מקורות

דרישת התרגיל היא להציג את המקטעים שעליהם התבססה התשובה. מצד שני, הבוט משמש את בני המשפחה עצמם, ולא רצוי שיוכלו לקרוא את הטקסט הגולמי שנכתב על כל אחד מהם.

**הפתרון:** הממשק מציג את התשובה בלבד, ולכל שאלה **המקורות מודפסים בטרמינל (ובלוג השרת ב-Render)**:

```
============================================================
שאלה: <השאלה, אחרי ניסוח מחדש>
score: 0.78 | source: <שם הקובץ>
<400 התווים הראשונים של המקטע>
------------------------------
...
תשובה: <התשובה שנשלחה לממשק>
```

כך אפשר לבדוק ולתעד את איכות האחזור, בלי לחשוף את המידע הגולמי למשתמשים.
חשוב לציין: הסתרת המקורות אינה מסתירה את התוכן עצמו, כי הבוט יכול לנסח אותו בתשובה. ההגנה האמיתית היא ההחלטה מה נכנס למאגר מלכתחילה (ראו [פרטיות ואבטחה](#פרטיות-ואבטחה)).

## בדיקות ודוגמאות

הבדיקות נעשו דרך הממשק, ואיכות האחזור נבדקה לפי המקורות שהודפסו בטרמינל. סוגי השאלות שנבדקו:

| # | סוג השאלה | דוגמה (בשמות בדויים) | ההתנהגות שנבדקה |
|---|---|---|---|
| 1 | שאלה ישירה על אדם | "מתי יום ההולדת של ישראל?" | שליפת הקובץ הנכון ותשובה מדויקת |
| 2 | שאלת המשך | "ומה התחביבים שלו?" | ניסוח מחדש עם השם הנכון ושליפה נכונה |
| 3 | שאלה על זוג / כמה אנשים | "ספר לי על ישראל ושרה" | שילוב מידע מכמה מקטעים, בפסקאות קצרות |
| 4 | שאלה שאין לה תשובה במאגר | "מי היה באירוסין של ...?" | אמירה שאין מידע מהימן, ניחוש מסומן והזמנה לספר |
| 5 | שאלה על הבוט עצמו | "מה מקורות המידע שלך?" | סירוב מנומס והחזרה לתפקיד |
| 6 | שאלה כללית על הבוט והמשתמש | "מי אני ומה שמי?" | תשובה זהירה, בלי המצאת פרטים |

### דוגמאות מלאות עם המקורות שאוחזרו

השמות בדוגמאות הוחלפו בשמות בדויים. מכל מקור מוצגים שם הקובץ וה-score; הטקסט עצמו קוצר.

#### דוגמה 1 – שאלה על כינוי של נכדה

**שאלה:** מי במשפחה מכונה נועה?

| # | score | מקור | מה יש בו |
|---|---|---|---|
| 1 | 0.527 | `שרה_לוי.txt` | פרטי הבת הבכורה ורשימת ילדיה |
| 2 | 0.524 | `מרים_גולד.txt` | ימי הולדת של ילדים, עיר ועיסוק |
| 3 | 0.524 | `רבקה_כהן.txt` | **רשימת הילדים, ובה "נועה כהן" – המקור הנכון** |
| 4 | 0.521 | `משפחה_כללי.txt` | רשימת ילדי ההורים, כתובת, סבים |
| 5 | 0.518 | `אבא.txt` | פרטי אבי המשפחה ורשימת ילדיו |

**תשובה:** "נועה כהן היא אחת הבנות של רבקה'לה (רבקה) ושמואל כהן, והיא נכדה של אבא ואמא. רוצה לשמוע עוד על ימי נישואין ואירועים מיוחדים במשפחה, או אולי על גודל המשפחה והמנהגים שלנו?"

**ניתוח:** התשובה נכונה, וההצעה להמשך עומדת בכלל "לא להציע לדבר על אדם אחר". אבל המקור הנכון דורג רק שלישי, וכל חמשת ה-scores קרובים מאוד זה לזה (0.518–0.527). זה מראה שהחיפוש הווקטורי מבחין רק בקושי בין קבצים שבנויים באותה תבנית ומלאים בשמות, וממחיש את חשיבות הבחירה ב-`top_k=5`: עם `top_k=2` המקור הנכון לא היה נשלף כלל.

#### דוגמה 2 – שאלה שאין לה תשובה במאגר

**שאלה:** שאלה על הסיפור שמאחורי השידוך של זוג במשפחה.

**המקורות שנשלפו (חלקי):** בין היתר `סבא.txt` (0.468), `שרה_לוי.txt` (0.463) ו-`אבא.txt` (0.462) – קבצים שאינם קשורים לשאלה, עם scores נמוכים בבירור מאלה של דוגמה 1.

**תשובה:** "אין לי מידע מהימן על הסיבות הספציפיות או הסיפור המדויק שמאחורי ההחלטה ... אני לא יודע בוודאות, אבל אפשר לנחש ש[...] השניים פשוט מצאו שפה משותפת והתאמה מצוינת. רוצה לספר לי את הסיפור שמאחורי השידוך שלהם?"

**ניתוח:** הבוט פועל לפי שלושת השלבים של כלל המידע החסר (אתגר 3): מצהיר שאין מידע, מציע ניחוש מסומן בבירור, ומזמין לספר. ה-scores הנמוכים של המקורות מעידים שאין במאגר מקטע רלוונטי.

#### דוגמה 3 – שאלה תלוית זמן (לפני השיפור)

**שאלה:** למי יש יום הולדת השבוע?

**תשובה (לפני השיפור):** "אין לי מידע מהימן לגבי התאריך של השבוע הנוכחי, ולכן אני לא יודע למי מבין בני המשפחה יש יום הולדת ממש השבוע. רוצה לספר לי באיזה תאריך עברי אנחנו נמצאים היום...?"

**ניתוח:** ראו [אתגר 4](#4-שאלות-תלויות-זמן-למי-יש-יום-הולדת-השבוע). אחרי השיפור, לוח האירועים המחושב מופיע כמקור נוסף (`לוח_אירועים_מחושב`, score=1.0), והתשובה מבוססת עליו.

> **להשלמה:** עוד שתי דוגמאות מפלט הטרמינל לפחות (מומלץ: שאלת המשך, ושאלת "למי יש יום הולדת השבוע?" אחרי השיפור), עם שמות בדויים.

## אתגרים ופתרונות

### 1. שילוב עברית ואנגלית: חיסכון בטוקנים מול איכות התשובה בעברית

**הבעיה:** ההוראות לבוט (system prompt) נשלחות למודל בכל שאלה מחדש. הן נכתבו תחילה בעברית, שצורכת מספר טוקנים גבוה משמעותית מאנגלית עבור אותו תוכן, ולכן כל שאלה הייתה יקרה ואיטית יותר. מעבר לאנגלית יצר שני סיכונים חדשים: שהמודל יענה באנגלית או ישלב מילים לועזיות, ושתשובה עברית תוצג בצורה שבורה בממשק (טקסט מעורב, סימני פיסוק ורשימות בצד הלא נכון).

**הפתרון:**
- **הפרדה בין שפת ההוראות לשפת התוכן:** ההוראות (`prompts.py`) נכתבו באנגלית, לחיסכון בטוקנים ולהבנה מדויקת יותר של המודל. המידע במאגר נשאר בעברית, כדי שה-embeddings של השאלה (בעברית) ושל המקטעים יהיו באותה שפה, ושהשליפה תהיה מדויקת.
- **הוראות שפה מפורשות:** "Always answer in Hebrew" ו-"Avoid English words and Latin characters", וגם שלב הניסוח מחדש (`condense_prompt`) הונחה במפורש להשאיר את השאלה בעברית, כדי שהחיפוש במאגר יתבצע בשפת המסמכים.
- **התאמה לתצוגה מימין לשמאל:** הוראה לכתוב בפסקאות קצרות, בלי תבליטים, כותרות, טבלאות ושורות "שדה: ערך", שנוטות להישבר בתצוגת RTL. בממשקים הוגדר `direction: rtl` לכל רכיבי הצ'אט, כולל רשימות.
- **הפרדה בין עובדות להוראות:** עובדות על בני המשפחה נשמרות רק במאגר, ולא ב-prompt. כך ה-prompt קצר, והעובדות נשלחות רק כשהן רלוונטיות לשאלה.

**התוצאה:** prompt קצר וזול יותר, תשובות בעברית תקינה, ותצוגה קריאה מימין לשמאל.

---

### 2. היעדר זיכרון שיחה: הבוט לא הבין שאלות המשך

**הבעיה:** בגרסה הראשונה (`as_query_engine`) כל שאלה טופלה כשאלה עצמאית. אחרי "ספר לי על ישראל", השאלה "ומה התחביבים שלו?" נכשלה: הבוט לא ידע על מי מדובר. מעבר לחוויה הלא טבעית, הייתה כאן בעיית **אחזור**: וקטור השאלה "ומה התחביבים שלו?" לא מכיל שם, ולכן החיפוש במאגר החזיר מקטעים אקראיים. הוספת ההיסטוריה למודל השפה לבדה לא הייתה פותרת את זה, כי הבעיה מתרחשת עוד לפני שלב היצירה.

**הפתרון:** מעבר ל-chat engine במצב `condense_plus_context`:
1. **ניסוח מחדש (condense):** לפני החיפוש, המודל משכתב את שאלת ההמשך לשאלה עצמאית לפי ההיסטוריה ("ומה התחביבים שלו?" ← "מה התחביבים של ישראל?").
2. **חיפוש** במאגר לפי השאלה המנוסחת.
3. **יצירת תשובה** עם ההקשר שנשלף ועם היסטוריית השיחה.

הזיכרון (`ChatMemoryBuffer`, עד 3000 טוקנים) נפרד לכל שיחה: ב-Streamlit ב-`st.session_state`, ובשרת במילון `chat_engines` לפי `session_id` שהדפדפן יוצר. כך שני בני משפחה שמשתמשים בבוט באותו זמן לא "מערבבים" שיחות.

**המחיר:** קריאה נוספת למודל בכל שאלה (שלב הניסוח מחדש), ושליחת ההיסטוריה. המגבלה של 3000 טוקנים שומרת על העלות בשליטה.

**בעיית המשך – אובדן הזיכרון אחרי הפעלה מחדש של השרת:** הזיכרון נשמר בזיכרון של תהליך השרת בלבד. ב-Render בתוכנית החינמית השרת נרדם אחרי זמן ללא שימוש, ולכן כשמשתמש חזר לשיחה ישנה מהרשימה, הבוט "שכח" את ההקשר.
**הפתרון:** הדפדפן שולח עם כל הודעה גם את היסטוריית השיחה (עד 20 ההודעות האחרונות). אם לשרת אין עדיין מנוע לשיחה הזו, הוא משחזר ממנה את ה-`ChatMemoryBuffer` לפני המענה. כך הזיכרון שורד גם הפעלה מחדש של השרת.

### 3. מידע חסר: מתשובת "אין מידע" יבשה לרצף שיחה טבעי

**הבעיה:** בהתאם לעיקרון "לענות רק מהמאגר", על שאלות שאין להן תשובה (למשל על אירוע משפחתי או סיפור שלא תועד) הבוט ענה בתשובה קבועה ויבשה. מבחינה טכנית זו התנהגות נכונה, אבל השיחה "נתקעה": המשתמש לא ידע איך להמשיך, והחוויה הרגישה כמו שאילתה למסד נתונים ולא כמו שיחה משפחתית.

**הפתרון:** הגדרת התנהגות בשלושה שלבים למידע חסר:
1. **שקיפות:** לומר בקצרה, ובמילים שלו בכל פעם, שאין לו מידע מהימן על כך.
2. **ניחוש מסומן (כשמתאים):** להציע ניחוש הגיוני על סמך מה שידוע (למשל, מי סביר שהשתתף באירוע משפחתי), עם סימון מפורש: "אין לי על זה מידע מהימן, אבל נראה לי ש...".
3. **הזמנה לספר:** להזמין את המשתמש לשתף ("רוצה לספר לי איך היה?"), ובמקרה הזה לא להסיט לנושא אחר. כשהמשתמש מספר, הבוט מגיב בקצרה ובחום רק לפי מה שסופר, ולא מבטיח "לזכור" את זה (כי המידע אינו נשמר במאגר).

**גבולות מוגדרים:** אין ניחושים בנושאים רגישים: ילדים, בריאות, כסף, מחלוקות או כל דבר שעלול להביך.

**האיזון:** כאן היה מתח בין דרישת ה-RAG (נאמנות למקורות, Groundedness) לבין חוויית שיחה טבעית. הפתרון שומר על הנאמנות: עובדה ממשית מגיעה רק מהמאגר, ומה שמעבר לה מסומן בבירור כניחוש. ההזמנה לספר הופכת "חור" במאגר להמשך טבעי של השיחה.

---

### 4. שאלות תלויות זמן: "למי יש יום הולדת השבוע?"

**הבעיה:** לשאלה, שהיא מהשאלות הנפוצות בבוט משפחתי, הבוט ענה שאין לו מידע על התאריך הנוכחי (ראו דוגמה 3). בניתוח התגלו **שתי בעיות נפרדות**:
1. **המודל לא יודע מה התאריך היום.** למודל שפה אין שעון, ושום מקטע במאגר לא מכיל את התאריך הנוכחי.
2. **גם אילו ידע, האחזור לא היה מספק את המידע.** השאלה חוצה את כל המשפחה: תאריכי הלידה מפוזרים בכל הקבצים, כולל עשרות נכדים, ו-`top_k=5` שולף רק חמישה מקטעים. בנוסף, וקטור השאלה ("השבוע") לא דומה סמנטית לשום תאריך עברי מסוים, ולכן חיפוש וקטורי אינו כלי מתאים כאן. וגם כשהמידע מגיע, מודלי שפה אינם אמינים בחישובים על תאריכים עבריים (מעבר בין חודשים, השוואת תאריכים באותיות, שנה מעוברת).

**החלופות שנשקלו:**

| חלופה | למה לא נבחרה |
|---|---|
| להוסיף ל-prompt רק את התאריך של היום | פותרת רק את הבעיה הראשונה; התשובה הייתה נשארת חלקית ולא אמינה |
| לשמור גם תאריכים לועזיים | יום הולדת עברי חל בכל שנה בתאריך לועזי אחר, ולכן היה צריך לעדכן את כל הקבצים מדי שנה |
| קובץ "לוח שנה" לפי חודשים במאגר + התאריך ב-prompt | האחזור עדיין לא מובטח (התאריך לא משתתף בחיפוש), החישוב נשאר אצל המודל, וכל תאריך היה נשמר פעמיים – מתכון לסתירות |

**הפתרון: חישוב דטרמיניסטי בקוד (`family_calendar.py`):**
1. **התאריך העברי של היום** מחושב עם הספרייה `pyluach`, לפי שעון ישראל (גם כשהשרת ב-Render רץ בשעון UTC).
2. **קריאת התאריכים מקבצי האנשים** עם ביטויים רגולריים: תאריך הלידה של האדם, של בן או בת הזוג, של הילדים, ויום הנישואים. המרת האותיות למספרים (כ"ה ← 25) נעשית בגימטריה. כך יש **מקור אמת אחד**: מעדכנים תאריך רק בקובץ של האדם. יום הנישואים של ההורים, שמופיע אצל שניהם, נספר פעם אחת, ומי שנפטר אינו נכלל.
3. **חישוב האירועים ב-7 הימים הקרובים** (היום ועוד שישה ימים), עם כללים לשנה מעוברת: מי שנולד באדר חוגג בשנה מעוברת באדר ב'; מי שנולד באדר א' חוגג באדר א' (ובשנה פשוטה – באדר); מי שנולד באדר ב' חוגג בשנה פשוטה באדר. יום ל' בחודש שיש בו השנה 29 ימים בלבד עובר לא' בחודש הבא.
4. **החיבור ל-LlamaIndex:** מחלקה `CalendarPostprocessor` (מסוג `BaseNodePostprocessor`) מוסיפה לכל תוצאת חיפוש מקטע נוסף, "לוח אירועים מחושב", שמכיל את התאריך של היום ואת האירועים הקרובים. היא מועברת ל-chat engine בפרמטר `node_postprocessors`, ולכן לא נדרש שינוי במבנה ה-RAG. המקטע מופיע גם ברשימת המקורות בטרמינל, וכך אפשר לבדוק בדיוק מה המודל קיבל.
5. **הוראה ב-prompt:** להסתמך על הלוח המחושב בכל שאלה על תאריכים ולא לחשב תאריכים בעצמו.

**דוגמה למקטע שנוסף (בשמות בדויים):**
```
לוח אירועים מחושב (מדויק, לא לחשב תאריכים בעצמך):
היום: יום שני, כ״ב חשון תשפ״ז (2.11.2026).
ימי הולדת ב-7 הימים הקרובים: שרה ישראלי: כ״ב חשון, יום שני (היום); ישראל ישראלי: כ״ו חשון, יום שישי (בעוד 4 ימים).
ימי נישואים ב-7 הימים הקרובים: ישראל ושרה ישראלי: כ״ז חשון, שבת (בעוד 5 ימים).
```

**המחיר:** כ-100 טוקנים נוספים בכל שאלה. בתמורה, הבוט יודע גם לענות על שאלות כמו "איזה תאריך היום?" או "כמה ימים עד יום ההולדת שלי?".

**הלקח:** RAG אינו הכלי הנכון לכל שאלה. אחזור וקטורי מצוין למציאת **טקסט דומה**, אבל לא לשאלות של **סינון וחישוב** על פני כל המאגר (כמו "כל מי שחוגג השבוע"). את אלה עדיף לחשב בקוד, ולתת למודל רק לנסח את התוצאה.

**מגבלה ידועה:** התאריך העברי מתחלף בחצות ולא בשקיעה.

### 5. תשובות בנאליות ומשעממות: העלאת ה-Temperature

**הבעיה:** בהגדרות ברירת המחדל התשובות היו נכונות עובדתית, אבל שבלוניות: ניסוחים חוזרים, מבנה זהה בכל תשובה, ותחושה "רובוטית" שלא מתאימה לבוט משפחתי.

**הפתרון:**
- **העלאת ה-temperature ל-1.3** (בטווח 0–2 של Gemini), כדי לקבל ניסוחים מגוונים וחיים יותר.
- **הוראה לא לחזור על משפטים קבועים**, למשל בתשובות "אין מידע".
- **מתן מקום ליצירתיות מבוקרת:** מותר להשלים פרטים לפי היגיון, בתנאי שמה שמעבר לעובדות מסומן כניחוש.

**למה זה בטוח במערכת RAG:** ה-temperature משפיע על **הניסוח**, ולא על **מה שנשלף**. האחזור הוא וקטורי ודטרמיניסטי, והעובדות מגיעות מהמקטעים. הסיכון בטמפרטורה גבוהה הוא "המצאות", ולכן העלייה לוותה בהוראות מפורשות לא להמציא עובדות ולסמן כל ניחוש.

---

### 6. תופעת לוואי: סגנון חנפני ונלהב מדי

**הבעיה:** אחרי העלאת ה-temperature, ויחד עם ההוראה לטון "חם ומשפחתי", הבוט נטה להגזמה: פתיחות כמו "איזו שאלה נהדרת!", ערימות של תארים ושבחים מוגזמים לכל בן משפחה. התשובות איבדו אמינות.

**הפתרון:** הגדרה מדויקת יותר של הטון: "חם וידידותי, אבל מבוסס ואמין, כמו בן משפחה שמכיר את הפרטים". נוסף כלל מפורש נגד חנופה: בלי סופרלטיבים, בלי מחמאות לשואל, בלי פתיחות נלהבות, ולכל היותר נגיעה חמה אחת בתשובה, ורק כשהיא מבוססת על עובדה. העיקרון: **המשפחתיות נובעת מההיכרות עם הפרטים, לא מהשבחים.**

**הלקח:** שינוי פרמטר אחד (temperature) השפיע על התנהגות שנראתה לא קשורה (טון). לכן כל שינוי נבדק מחדש על אותן שאלות.

---

### 7. מבנה התשובה: גוש טקסט אחד

**הבעיה:** הוראה מוקדמת ("לענות בפסקה אחת") גרמה לתשובות ארוכות להופיע כגוש טקסט אחד, קשה לקריאה, במיוחד בטלפון. מצד שני, רשימות ותבליטים נשברו בתצוגה מימין לשמאל.

**הפתרון:** הוראה לכתוב בפסקאות קצרות (משפט עד שלושה, רעיון אחד בכל פסקה) עם שורה ריקה ביניהן; תשובה קצרה בפסקה אחת וארוכה בשתיים–שלוש; ההצעה להמשך בפסקה נפרדת בסוף. בממשק ה-React כל שורה ריקה מוצגת כפסקה נפרדת. בנוסף, הבוט מתבקש לא "לשפוך" את כל הפרטים, אלא לבחור את מה שמתאים לשאלה ולהציע להרחיב.

---

### 8. חלוקה למקטעים: קבצים קצרים התפצלו

**הממצא:** הציפייה הייתה שכל קובץ (אדם) יישמר כמקטע אחד, אבל גם קבצים קצרים פוצלו לשניים או שלושה מקטעים.
**ההסבר:** `SentenceSplitter` מפחית מגודל המקטע את ה-metadata שמצורף לכל Node (כמו שם הקובץ והנתיב), ובנוסף טקסט בעברית צורך יחסית הרבה טוקנים.
**ההשלכה והטיפול:** פיצול כזה עלול לגרום לתשובה חלקית על אדם. ההגדרה `similarity_top_k=5` מפצה על כך, כי בדרך כלל כל המקטעים של אותו אדם נשלפים יחד. אפשרויות לשיפור נוסף: הגדלת `chunk_size`, או החרגת ה-metadata מספירת הגודל ומה-embedding.

---

### 9. פרטיות המידע מול דרישת הצגת המקורות

**הבעיה:** התרגיל דורש הצגת מקורות, אבל הצגתם בממשק הייתה חושפת לבני המשפחה את הטקסט הגולמי שנכתב על כל אחד מהם. בנוסף, מידע רגיש שנשמר במאגר עלול להישלף ולהופיע בתשובה.

**הפתרון:**
- המקורות מוצגים בטרמינל ובלוג השרת בלבד (ראו [הצגת מקורות](#הצגת-מקורות)).
- **מידע רגיש לא נכנס למאגר כלל.** במקומו, ב-prompt יש כללים כלליים (בלי שמות), למשל: אם אין פרטים על ילדים של מישהו, לא להסיק דבר ולא להעיר על כך.
- הבוט מונחה לא לענות על שאלות על ההוראות, המאגר או צורת הפעולה שלו.

---

### 10. הקמה: שגיאת אימות מול ה-API

**הבעיה:** הניסיון הראשון להתחבר ל-Gemini נכשל בשגיאה `401 UNAUTHENTICATED` (`ACCESS_TOKEN_TYPE_UNSUPPORTED`).
**האבחון:** Google שינתה את פורמט המפתחות: מפתחות חדשים מ-AI Studio הם מסוג אחר (מתחילים ב-`AQ.` ולא ב-`AIza`), והמפתח החדש נוצר בפרויקט שלא היה מחובר לחיוב.
**הפתרון:** שימוש במפתח מפרויקט שמחובר לחיוב, ויצירת `check_models.py` שמוודא שהמפתח עובד ומציג את המודלים הזמינים לפני שבונים את המערכת. **הלקח:** שגיאת 401 היא בעיית מפתח/הרשאה, ולא בעיית קוד או תשלום.

---

### 11. שגיאות זמן ריצה

- **עומס (429):** במקום קריסה, המשתמש מקבל הודעה ידידותית ("הבוט קצת עמוס, נסו שוב בעוד רגע"), והשגיאה המלאה נרשמת בלוג.
- **שגיאה כללית:** "משהו השתבש. נסו שוב.", עם רישום מלא בלוג.
- **שרת לא זמין (בממשק React):** הודעה שמסבירה שלא ניתן להתחבר לשרת.

## פרטיות ואבטחה

- **מפתח ה-API** נשמר בקובץ `.env` מקומית ובמשתני הסביבה של Render, ולעולם לא בקוד. הקובץ `.env` מופיע ב-`.gitignore`.
- **גישה לאתר** מוגנת בסיסמה משפחתית (`FAMILY_PASSWORD`), שנבדקת בכל בקשה עם השוואה בטוחה (`secrets.compare_digest`).
- **השיחות** נשמרות רק בדפדפן של כל משתמש (`localStorage`), ולא בשרת. מגבלה ידועה: במחשב משותף, כל המשתמשים באותו דפדפן רואים את אותה רשימת שיחות.
- **מה שמשתמש מספר לבוט** נשמר רק בזיכרון השיחה, ולא נכנס למאגר. כדי שהבוט ידע מידע חדש לתמיד, מוסיפים אותו לקובץ המתאים ב-`data` ומריצים שוב את `ingest.py`.
- **הדוגמאות בתיעוד** נכתבו עם שמות בדויים.

## כיווני שיפור עתידיים

- **השוואת אסטרטגיות Chunking** (256 מול 512 מול 1024 טוקנים) על סט שאלות קבוע.
- **השוואת top_k** (3 מול 5): האם פחות מקטעים מפחיתים ערבוב פרטים בין אנשים?
- **Query Expansion** לשאלות בכינויים, או הוספת שורת "מכונה גם:" לכל קובץ.
- **Reranking** לשיפור סדר המקטעים שנשלפו.
- **Metadata Filtering** לפי אדם, כשהשאלה מזכירה שם במפורש.
- **הערכה במדדים:** Recall@k לאחזור ו-Faithfulness לתשובות.
- **התחברות משתמשים**, כדי שרשימת השיחות תהיה אישית גם במחשב משותף.
